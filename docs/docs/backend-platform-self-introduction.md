# 백엔드/플랫폼 자기소개서 초안

## 핵심 문장

저는 게임 서버 구현을 위해 만들기 시작한 `io_uring` 기반 서버 엔진을 공통 네트워크 I/O 실행 엔진으로 분리하며, 연결 수명, 버퍼 소유권, 송신 순서, 흐름 제어 문제를 구조적으로 해결해 왔습니다. 이후 이 엔진을 클라우드 서버에서 직접 운용하며 TCP 게임 서버, 웹 서버, 프록시 서버로 확장해 여러 서비스가 공유할 수 있는 실행 기반인지 검증했습니다.

## 자유형 본문

Linux `io_uring` 기반 게임 서버를 구현하면서 멀티스레딩과 비동기 I/O 환경의 문제를 직접 다뤘습니다. 처음에는 패킷 처리, Room, 브로드캐스트 같은 게임 서버 기능이 중심이었지만, 클라이언트 연결을 독립적인 실행 단위로 추상하다 보니 게임 로직보다 아래에 있는 네트워크 I/O 실행 문제가 반복해서 드러났습니다.

패킷 처리 계층이 패킷 경계뿐 아니라 연결 종료, 수신 재등록, 송신 큐, timeout, cancel까지 모두 알게 되면 프로토콜 로직과 네트워크 I/O 로직이 강하게 결합됩니다. 이 구조로는 HTTP 서버나 프록시 서버로 확장할 때 같은 연결 관리 코드를 다시 만들 가능성이 컸습니다. 그래서 게임 도메인에 묶이지 않는 공통 네트워크 I/O 실행 엔진으로 책임을 분리했습니다.

1. 완료 통지 기반 I/O에서는 수명과 해제 판단을 단순한 포인터 소유권 이전으로 처리하기 어려웠습니다.

`io_uring` 작업은 세션 종료 요청보다 늦게 완료 통지로 돌아올 수 있습니다. 세션을 목록에서 제거했다는 이유만으로 객체나 버퍼를 해제하면 늦은 완료 통지가 사라진 대상에 접근할 수 있습니다. 이를 막기 위해 개별 I/O 이벤트의 완료 상태와 세션 전체의 미완료 작업 수를 따로 추적했고, 모든 완료 통지가 정리된 뒤에만 세션을 해제하도록 분리했습니다.

2. 부분 전송이 발생하면 애플리케이션이 의도한 메시지 순서를 커널이 그대로 보장해 주지 않았습니다.

두 메시지를 순서대로 보내더라도 부분 송신이 발생하면 첫 번째 메시지의 남은 바이트와 두 번째 메시지가 섞일 수 있습니다. 그래서 연결마다 하나의 활성 송신 작업만 허용하고, 나머지는 순서가 보장되는 송신 대기열에 쌓았습니다. 완료 통지가 돌아올 때마다 송신 위치를 전진시키고, 현재 메시지가 끝난 뒤에만 다음 메시지를 제출하도록 했습니다.

3. 독립적인 세션이 아니라 여러 세션이 묶인 Room에서는 내부 상태 변화 순서가 실제 전송 순서로 이어진다는 보장이 없었습니다.

Room의 논리적 브로드캐스트 순서와 실제 세션 송신 대기열에 들어가는 순서는 서로 어긋날 수 있었습니다. 이를 해결하기 위해 Room의 상태 결정 순서, 워커 간 출력 전달 순서, 실제 소켓 송신 순서를 각각 다른 직렬화 경계로 나눴습니다. 각 단계가 보장해야 하는 순서를 분리해 Room 내부 순서와 세션 송신 순서를 함께 보존했습니다.

4. 송신과 수신의 속도 차가 커지면 한쪽 큐나 버퍼가 무제한으로 쌓이는 문제가 있었습니다.

생산자가 데이터를 만드는 속도보다 소켓 송신 완료가 느리면 송신 대기열이 계속 증가합니다. 그래서 송신 대기열을 메모리 압력 경계로 보고, 쌓인 데이터의 크기와 대기 상태를 관측했습니다. 프록시에서는 쓰기 쪽 압력을 읽기 일시 정지로 되돌리고, HTTP 응답은 큰 본문을 한 번에 만들지 않고 비워지는 속도에 맞춰 조각 단위로 생산하도록 설계했습니다.

이 과정에서 공통 실행 엔진은 프로토콜을 해석하지 않고 바이트 스트림, 세션 수명, 버퍼 소유권, 송신 순서, 흐름 제어만 책임지도록 정리했습니다. 그 위에서 게임 모듈은 패킷 해석과 Room 실행 모델을, 웹 모듈은 HTTP 파서와 라우팅을, 프록시 모듈은 스트림 중계와 TLS/SNI 라우팅을 담당하도록 분리했습니다. 결과적으로 게임 서버를 위해 시작한 엔진을 여러 서버 애플리케이션이 공유할 수 있는 네트워크 I/O 실행 기반으로 확장했습니다.

검증은 "`io_uring`이 빠르다"가 아니라 병목을 분리해 보는 방식으로 진행했습니다. Core echo로 전송 경로를, Game 브로드캐스트와 Room 분산으로 fan-out 병목을 확인했습니다. 이후 클라우드 서버에서 TCP 게임 서버, Web, Proxy 형태로 직접 운용하며 Core 내부 불변식이 유지되는지 검증했습니다. 이 경험을 통해 백엔드/플랫폼 개발에서 중요한 것은 반복되는 문제를 공통 실행 규칙으로 정리하고, 그 규칙이 깨지지 않는지 확인하는 일이라고 배웠습니다.
