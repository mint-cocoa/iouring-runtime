
클라이언트와 서버 간의 연결을 `Session`으로 추상화하면 “세션이 살아 있다”는 말이 여러 의미로 나누어집니다.

| 의미 | 설명 |
| --- | --- |
| 관리 대상 생존 | `SessionManager`의 연결 목록에 남아 있음 |
| 콜백 대상 생존 | CQE 콜백을 실행하는 동안 `Session` 객체가 파괴되지 않음 |
| 제출 I/O 생존 | 이미 커널에 제출된 I/O의 CQE가 아직 돌아올 수 있음 |
| 논리 상태 생존 | 새 수신, 송신, 등록 작업을 받아도 되는 상태임 |

이 의미들을 하나의 소유권 규칙으로 합치면 종료 경로가 불명확해집니다. 예를 들어 `SessionManager`에서 세션을 제거했다고 해서 이미 제출된 CQE가 더 이상 오지 않는 것은 아닙니다. 반대로 pending I/O가 남아 있다고 해서 외부에서 정상 연결된 세션으로 취급해야 하는 것도 아닙니다.

따라서 이 코드에서는 수명 관리 장치를 하나의 소유권 이야기로 합치지 않고, 각 장치가 판단하는 범위를 분리했습니다.

| 장치                   | 판단 범위       | 결정하는 것                          |
| -------------------- | ----------- | ------------------------------- |
| `SessionManager`     | 애플리케이션 관리   | 외부에서 연결된 세션으로 취급할지              |
| `OwnerBoundEvent`    | 콜백 내부 생존    | 제출 이벤트가 owner 생존과 handler 호출을 함께 보장할지 |
| `DispatchResult`     | 이벤트 객체 생존   | 이번 CQE 이후 이벤트 객체를 완료, 유지, 재사용할지 |
| `pending_io_`        | 세션 전체 제출 추적 | 아직 최종 CQE가 돌아오지 않은 제출 I/O가 있는지  |
| `SessionState`       | 세션 논리 상태    | 새 작업 허용 여부와 종료 단계               |

## 제출된 I/O와 콜백 대상 생존

`SessionManager`는 외부에서 세션을 “현재 연결된 세션”으로 취급하는 동안의 소유자입니다. 하지만 이것만으로는 이미 `io_uring`에 제출된 I/O의 CQE 콜백 대상 생존을 보장할 수 없습니다.

`io_uring`에는 콜백 객체를 직접 실을 수 없습니다. SQE의 `user_data`에는 제출된 I/O 하나를 대표하는 `IoEvent*`만 저장하고, CQE가 도착하면 같은 `IoEvent*`를 복원해 완료 처리를 위임합니다.

```cpp
auto* ev = reinterpret_cast<IoEvent*>(data);
const auto dispatch_result = ev->Complete(result, flags);
```

`IoRing`은 이 이벤트가 `Session` 작업인지, `Listener` 작업인지 알 필요가 없습니다. `IoEvent::Complete()`를 호출하면, 이벤트 객체의 가상 `Dispatch()`가 실행되고 각 operation 타입이 자기 owner의 처리 함수로 넘깁니다.


```
SessionManager
  └── 외부에서 접근 가능한 현재 연결 목록을 관리

RecvOp / SendOp / DisconnectOp / AcceptOp
  ├── 제출된 I/O 하나를 대표
  ├── owner shared_ptr 보관
  ├── CQE 완료 시 Dispatch() 실행
  └── owner의 실제 handler 호출

IoRing
  └── owner 타입을 모르고 IoEvent::Complete()만 호출
```

따라서 콜백 대상 생존은 `SessionManager`가 아니라 제출된 operation 객체가 보장합니다. `SessionManager`는 “현재 연결 목록”을 관리하고, `RecvOp`나 `SendOp` 같은 제출 이벤트는 “이미 커널에 제출된 I/O가 완료될 때까지 콜백 대상을 살려두는 책임”을 가집니다.

## `DispatchResult`와 `pending_io_`

CQE를 처리한 뒤에는 두 가지를 따로 판단해야 합니다.

1. 이번 CQE를 받은 `IoEvent` 객체를 끝내도 되는지
2. 세션 전체에서 아직 돌아오지 않은 제출 I/O가 남아 있는지

multishot 수신에서는 하나의 SQE가 여러 CQE를 만들 수 있습니다. 중간 CQE는 데이터를 하나 전달하지만, 같은 수신 제출은 계속 살아 있을 수 있습니다. 따라서 CQE 하나를 받았다고 해서 항상 제출 I/O 하나가 끝났다고 볼 수 없었습니다.

이를 분리하기 위해 이벤트 콜백은 `DispatchResult`를 반환하고, 세션은 제출 I/O 단위로 `pending_io_`를 관리합니다.

```cpp
auto* ev = reinterpret_cast<IoEvent*>(data);
const auto dispatch_result = ev->Complete(result, flags);
```

| 값 | 의미 |
|---|---|
| `kComplete` | 이번 CQE 처리 뒤 이벤트 객체를 완료 처리할 수 있음 |
| `kPending` | 이번 CQE 처리 뒤에도 이벤트 객체를 유지해야 함 |

| 경로                  | CQE 의미                                  | `DispatchResult` | `pending_io_` 처리     |
| ------------------- | --------------------------------------- | ---------------- | -------------------- |
| 단일 송신 완료            | 제출한 send 하나가 끝남                         | `kComplete`      | 감소                   |
| 짧은 쓰기               | 같은 `SendOp`를 남은 바이트 범위의 새 send SQE에 재제출 | `kPending`       | 재제출 성공 시 유지, 실패 시 감소 |
| multishot 수신 중간 CQE | 데이터는 받았지만 같은 multishot 제출이 계속 살아 있음     | `kPending`       | 유지                   |
| multishot 수신 최종 CQE | multishot 제출이 종료됨                       | `kComplete`      | 감소                   |
| cancel/shutdown 완료  | 종료용 제출이 완료됨                             | `kComplete`      | 감소                   |

대표적인 경우는 두 가지입니다. 첫째, multishot receive에서 `IORING_CQE_F_MORE`가 붙은 CQE는 중간 완료입니다. 같은 수신 SQE에서 CQE가 더 올 수 있으므로 이벤트 객체를 유지하고, `pending_io_`도 감소시키지 않습니다.

두번째 문제는 커널에 요청한 send 가 부분적으로 전송되었을때 입니다.

이떄 CQE를 받은 뒤 같은 `SendOp`를 남은 바이트 범위의 새 send SQE에 다시 연결해야 하므로 이벤트 객체를 삭제하지 않고`kPending`을 반환합니다. 재제출이 성공하면 그대로 유지하고 재제출이 실패한 경우에만 `CompletePendingIo()`로 기존 제출분을 정리합니다.

`kComplete`는 이번 CQE 처리 뒤 이벤트 객체를 완료 처리할 수 있다는 뜻입니다. 단일 send 완료, cancel 완료, shutdown 완료, 또는 `IORING_CQE_F_MORE`가 없는 multishot 최종 CQE가 여기에 해당합니다.

##  종료 가능 상태 

`pending_io_`는 이미 제출된 I/O가 남았는지만 셉니다. 하지만 종료가 시작된 세션이 새 수신, 송신, 등록 작업을 받아도 되는지는 별도의 상태 판단입니다.

이를 위해 세션은 논리 상태를 가집니다.

| SessionState` | 의미                        |
| ------------- | ------------------------- |
| `kOpen`       | 정상 송수신 가능                 |
| `kClosing`    | 종료 시작, 새 일반 작업 차단         |
| `kDraining`   | 종료 관련 제출 이후 남은 CQE를 비우는 중 |
| `kClosed`     | 연결 종료 통지와 manager 해제 완료   |

종료 흐름은 “새 작업 차단 → 종료 관련 작업 제출 → 남은 CQE 비우기 → 한 번만 해제” 순서로 진행됩니다.

1. `Disconnect()`가 호출되면 `SessionState`를 `kClosing`으로 전환
    
2. `kOpen`이 아니면 새 수신, 새 송신, 새 등록 작업을 차단
    
3. 이미 큐에 들어간 송신 데이터는 정책에 따라 폐기하거나, 종료 전에 drain할지 결정
    
4. 취소, `shutdown`, close 관련 정리처럼 커널 제출이 필요한 종료 작업을 등록
    
5. 제출에 성공한 종료 작업은 `pending_io_`에 반영
    
6. CQE가 도착할 때마다 이벤트 dispatch가 `DispatchResult`를 반환
    
7. 최종 완료 CQE는 `pending_io_`를 감소
    
8. `ClosingStarted() && pending_io_ == 0 && !disconnected_notified_` 조건을 통과하면 `TryRelease()`가 `OnDisconnected()`와 manager 해제를 한 번만 실행
    
9. 해제가 끝나면 상태를 `kClosed`로 전환
    

`SessionState`가 없으면 이미 종료가 시작된 세션에 새 작업이 다시 들어갈 수 있습니다. 예를 들어 수신 CQE에서 `res == 0`을 보고 peer close를 감지해 종료를 시작했는데, 다른 경로의 `Send()`나 `RegisterRecv()`가 아직 세션을 정상 상태로 보고 새 SQE를 제출할 수 있습니다.

이 경우 다음과 같은 버그가 생길 수 있습니다.

| 버그                | 설명                                                             |
| ----------------- | -------------------------------------------------------------- |
| 종료 중 새 recv 등록    | 닫히는 세션에 multishot recv가 다시 걸려 종료가 끝나지 않음                       |
| send after close  | 이미 닫히는 소켓에 새 송신이 들어가 `EBADF`, `ECANCELED`, `EPIPE`류 오류가 뒤늦게 발생 |
| `pending_io_` 재증가 | drain 중이던 세션의 pending 카운터가 다시 증가해 해제 조건이 흔들림                   |
| 이중 연결 종료 통지       | 서로 다른 CQE 경로가 동시에 종료 조건을 만족해 `OnDisconnected()`가 중복 호출될 수 있음   |
| 이벤트/버퍼 수명 꼬임      | 종료 중 폐기한 송신 버퍼나 이벤트 객체를 늦은 CQE가 다시 참조할 수 있음                    |
| 세션 부활             | manager에서 제거해야 할 세션에 새 작업이 붙으면서 외부 관점의 종료 상태와 내부 I/O 상태가 어긋남   |

따라서 `SessionState`는 `pending_io_`와 별개로 이미 제출한 I/O가 남았는지를 판단하고, `SessionState`는 “지금 새 I/O를 받아도 되는지를 판단합니다.

## 해제 조건

세션 해제는 다음 조건이 모두 만족되어야 합니다.

```text
1. 세션이 종료를 시작한 상태.
2. 새 일반 작업이 차단되어 있음.
3. 이미 제출된 I/O의 최종 CQE가 모두 돌아왔다.
4. 종료 통지가 아직 실행되지 않았다.
```

이를 코드 관점으로 표현하면 다음과 같습니다.

```cpp
bool Session::CanRelease() const {
    return state_ != SessionState::kOpen
        && pending_io_ == 0
        && !disconnected_notified_;
}
```

`TryRelease()`는 이 조건을 통과한 경우에만 `OnDisconnected()`와 `SessionManager` 해제를 수행합니다. 또한 `disconnected_notified_`를 통해 동일 세션의 종료 통지가 한 번만 실행되도록 막습니다.

```cpp
void Session::TryRelease() {
    if (!CanRelease()) {
        return;
    }

    disconnected_notified_ = true;
    state_ = SessionState::kClosed;

    OnDisconnected();
    manager_->Remove(session_id_);
    
    //세션 소유자 실행 문맥에서 호출되어야 순서가 보장됨
}
```

### 결론

이 구조에서 각 장치는 같은 `Session`을 다루지만 서로 다른 경계를 다루고 있습니다.

| 구분       | `SessionManager` | `OwnerBoundEvent`                          | `SessionState`                              | `DispatchResult`        | `pending_io_`   |
| -------- | ---------------- | ------------------------------------------ | ------------------------------------------- | ----------------------- | --------------- |
| 대상       | 외부 연결 목록         | CQE 콜백 대상과 handler 바인딩                     | 세션 전체                                       | CQE를 받은 `IoEvent` 하나    | 세션이 제출한 I/O 전체  |
| 질문       | 외부에서 연결된 세션인가?   | 어떤 owner의 어떤 handler를 안전하게 호출할 것인가?        | 새 작업을 받아도 되는 상태인가?                          | 이번 CQE 뒤 이벤트를 유지해야 하나?  | 아직 최종 CQE가 남았나? |
| 대표 값     | manager map/list | `RecvOp`, `SendOp`, `AcceptOp`, `CancelOp` | `kOpen`, `kClosing`, `kDraining`, `kClosed` | `kComplete`, `kPending` | 정수 카운터          |
| 판단하는 것   | 외부 접근 가능성        | keep-alive와 멤버 handler 호출                  | 새 작업 허용과 종료 단계                              | 이벤트 완료, 유지, 재사용         | 해제 전에 기다릴 I/O 수 |
| 최종 해제 관계 | 제거 대상            | 콜백 중 생존 보장                                 | `kOpen`이 아니어야 함                             | 직접 판단하지 않음              | 0이어야 함          |
